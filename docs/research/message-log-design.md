# 訊息紀錄：功能與技術規劃

日期：2026-09-06。狀態：規劃完成，尚未實作、編譯或實機驗證。

配套文件：[逐階段施工與驗收](message-log-agent-tasks.md)。後續 agent 請兩份一起閱讀。

## 1. 目的與決策層級

玩家會忘記任務線索，因此需要在遊戲內查閱自己已經看過的對話與劇情原文。這不是自動任務追蹤器，不推測任務狀態、不提供未曾顯示的文本。

### 使用者已確認

- 每筆訊息包含 Who（NPC／說話者）、Where（地點）、When（現實世界時間）、What（內容）。
- 排除一般商店、旅店等交易行為的對話；可以收錄劇情演出文本。
- 每份遊戲存檔對應獨立訊息紀錄檔，不能改動現有遊戲存檔格式。
- 讀取舊存檔，訊息紀錄必須回到該次存檔時；不能保留之後或其他分支的訊息。
- 「遊戲選項」新增「訊息紀錄」按鈕。使用者接受放在「儲存進度」之後、「偏好設定」之前；其後按鈕下移，取消維持原位。
- 原始規劃預定交由後續 agent 施工；目前第 1–3 階段工程已依施工清單實作，實際狀態以進度文件為準。

### 本文件提出的預設方案

以下是可直接用於第一版工程的建議，不應誤報成使用者逐項指定：

- 依一場對話分組，逐段標示說話者，保留玩家實際選擇的話題／回答。
- 只排除交易用途，不排除整個場所；旅店老闆提供任務消息仍收錄。
- 畫面先做依時間瀏覽與分頁閱讀。人物／地點篩選列為後續階段；全文搜尋列為選配，DOS 中文輸入尚未確認，不能承諾現成可用。
- 每份存檔保存完整歷史複本；目前遊玩歷史使用磁碟工作檔，記憶體只留小型緩衝區。
- 缺少或損壞的附屬檔不阻止原遊戲讀檔，顯示紀錄缺失提示並開始新的可用紀錄區段，絕不挪用其他時間線。
- 第一版不納入一般書籍全文、任何戰鬥訊息、法術訊息、謎題提示與正文、物品說明、系統操作提示；劇情閱讀物若有任務需要，另列明確收錄規則。

## 2. 玩家行為規格

### 選項入口

```text
開始新遊戲
讀取進度
儲存進度
訊息紀錄  ← 新增
偏好設定
章節目錄
退出至 DOS

取消
```

沿用既有按鈕樣式。截圖是放大畫面，程式以 320×200 繪製；不能把截圖像素直接當按鈕座標。位置以解析 `req_opt0.dat`／`req_opt1.dat` 後的實際範圍為準。

- 遊戲內開啟：可查看已保存歷史與目前尚未存檔的新訊息。
- 未開始／未載入遊戲：按鈕停用；鍵盤也不能繞過停用狀態。
- 歷史為空：「目前尚無訊息紀錄」。舊檔缺少歷史則另顯示「此存檔沒有先前的訊息紀錄，將從現在開始記錄」。
- 返回或 Esc：回到遊戲選項；再按取消才回遊戲。
- 閱讀不推進世界模擬，不新增訊息，不重播事件，不改動任務旗標。
- 沿用目前 modal 滑鼠／FPS 模式進出規則，離開時恢復 palette、字型、繪圖頁、游標與輸入狀態。

### 紀錄畫面

320×200 下優先採兩頁模式，避免左右分欄擠壓中文：

1. 清單頁：標題、數筆對話摘要、上一頁／下一頁／閱讀／返回。預設選最新一場；長人名／地名可在摘要下一行呈現。
2. 內容頁：人物、地點、日期時間、逐段原文、上一頁／下一頁／返回清單。

本文字級以既有 16px 中文為優先；摘要是否使用現有小字型由實機可讀性決定。不要為多塞幾行改用新 renderer。長內容只能分頁，不得靜默截斷。新增按鈕、提示所需中文字必須進既有字庫生成流程。

時間顯示 `YYYY-MM-DD HH:MM:SS`。採顯示當下 DOS 系統日期時間；它是否與宿主 Windows 同步必須在發布用 DOSBox-X 設定中驗證。不要將 DOS 時鐘宣稱成已驗證的宿主時間。若不同步，須修正啟動／模擬器設定或回報限制，不能拿遊戲天數代替。

同一秒與系統時間倒退時，以遞增事件序號維持實際發生順序；不以時間戳當唯一 ID。每場保留開始時間，每段另保留發生時間。

## 3. 收錄與分類

| 內容 | 第一版處理 |
|---|---|
| NPC 故事、傳聞、任務提示 | 收錄 |
| 玩家實際選擇的話題／回答 | 收錄；不記錄未選選項 |
| 劇情旁白、已播放的過場文字 | 收錄實際顯示部分 |
| 買賣價格、成交、住宿確認、餘額不足 | 排除 |
| 商店／旅店中的劇情對話 | 收錄 |
| 戰鬥、法術、密碼／開鎖謎題訊息 | 全部排除 |
| 存讀檔提示、錯誤視窗、選單說明 | 排除 |
| 重繪、陰影繪製、上一頁回看 | 不產生重複紀錄 |
| 日後再次和同一 NPC 談相同話題 | 允許新的對話場次，不全域去重 |

分類使用「呼叫情境 + record key 精確覆寫」；禁止只用商店地圖、關鍵字或整個 DDX 區域排除。產出可維護的分類清單，逐筆有用途與遊戲案例。Python 建置階段可以使用 JSON；DOS 執行時使用小型生成表，不引入 JSON parser。

對已確認為敘事的呼叫路徑，未列入排除者預設收錄，避免漏線索。未知呼叫路徑先列調查表，不可因為經過 DIALOG 就全部收錄。交易、系統、章節載入展示、戰鬥、法術與謎題路徑必須明確標記。戰鬥、法術與謎題即使帶有敘事語氣也一律排除。

一场交談可包含多個 DDX 節點和玩家選項。最外層 NPC 互動開始／結束建立 conversation 範圍，巢狀事件沿用範圍；非 NPC 劇情建立獨立範圍。不能把每次 render 或每個遞迴 `dialog_play_record()` 都當一場交談。

## 5. 時間線與檔案生命週期

### 附屬檔布局

```text
GAMES\<既有目錄>.Gxx\SAVE01.GAM   原遊戲檔，格式不變
GAMES\<既有目錄>.Gxx\SAVE01.MLG   對應完整訊息歷史

<工作暫存位置>\MSGWORK.MLG       目前遊玩歷史，不列入存檔清單
```

所有名稱遵守 DOS 8.3。工作檔位置由既有 temp drive 規則決定，檔名避免與 TEMP.GAM 衝突；第一版假設單一遊戲執行個體使用同一資料目錄。暫存位置可與保存位置跨磁碟，提交用的暫存檔必須建在目標保存目錄，不能跨磁碟 rename。

- 成功新遊戲：新建空時間線，再加入這次新遊戲實際播放的劇情。
- 正常遊玩：append 至工作檔；不可直接 append 到來源存檔的 `.MLG`。
- 成功存檔：工作歷史複製成目標槽完整 snapshot，來源槽不變；保存動作本身不計入歷史。
- 成功讀檔：先驗證候選紀錄，替換目前工作歷史，序號從該快照後繼續。
- 取消讀檔／載入失敗：不得先清空或替換目前紀錄；原載入失敗若無法返回遊戲，沿用引擎處置，不聲稱實現遊戲狀態回滾。
- 正常章節推進：沿用時間線。章節目錄直接跳章不是自然推進，需依實際來源狀態決定恢復來源快照或新建歷史，不得沿用剛離開的任意分支。
- 遊戲重啟：殘留工作檔不是存檔，不自動恢復到任意槽位。診斷可以保留殘檔，但不做跨存檔合併。
- 搬移／備份：`.GAM` 和同名 `.MLG` 一起搬。只搬 `.GAM` 仍能遊玩，但無舊訊息。
- 刪除／輪替：同步處理對應 `.MLG`、本功能專屬暫存／備份；不得掃除其他副檔名的未知檔案。

### 必須成立的分支範例

```text
看到 1..10 → 存 A → 看到 11、12 → 存 B
讀 A → 只能看到 1..10 → 看到 13 → 存 C
B = 1..12；C = 1..10、13；A 仍是 1..10
```

覆蓋 A 後 A 改對應新快照；讀 A 的舊版本只有在玩家另外備份整對檔案時才可能。

### 轉場隔離

進入讀檔／新遊戲轉場前進入 `transition` 狀態，不能把讀檔畫面播放的章節字樣加入舊工作檔。讀既有存檔時，這種重播屬載入展示，不加入恢復後的歷史。新遊戲／自然換章的真正敘事則要收錄：可調整紀錄初始化時機，或先寫隔離的候選暫存、成功後合入新歷史；選擇須以呼叫順序證據支持。不能简单把所有轉場文本永久停記。

## 6. 寫入安全與失敗處理

`.GAM` 與 `.MLG` 不是單一原子檔案。兩次 rename 不等於原子交易。第一版要求「保護既有存檔、可恢復的一對檔案、辨識不匹配」；沒有證據時不得宣稱斷電絕對安全。

建議提供共同的 pair-save 協調器，手動、書籤、自動、快速存檔皆使用。`savegame_write()` 保持原序列化職責；協調器接收最終槽位路徑，不能把 autosave 的 `AUTONEW.GAM` 誤當最終紀錄名稱。

提交協議：

1. 完整遊戲快照已同步到 TEMP.GAM 後，以原序列化器寫目標目錄中的新 `.GAM` 暫存。
2. 驗證新遊戲檔；分塊計算整檔長度與 CRC32。將工作紀錄串流複製成新 `.MLG`，標頭綁定該長度／CRC32，驗證所有內容，檢查 close 結果。
3. 寫入小型交易標記，記下目標槽、是否原有 GAM／MLG、舊／新檔指紋。僅用已生成合法槽名，不信任檔案中的任意路徑。
4. 將舊對檔案移到各自備份，再移入新 GAM、新 MLG。每步检查返回值，失敗則走共同恢復程序。
5. 確認正式位置的新對檔案匹配後，才清理備份和交易標記，回報成功。

恢復不是只信交易標記的最後 phase：程式可能在 rename 成功、phase 尚未更新時中斷。每次列舉／載入／寫入前，根據實際正式檔、暫存檔、備份的存在與指紋判定：完整新對就完成提交；否則恢復完整舊對（包含「舊檔本來沒有 MLG」狀態）；兩者都無法成立則保留證據，提示紀錄不可用，不掛上不匹配歷史。恢復重跑必須得到同一結果。

CRC32 用於意外錯配偵測，不是安全簽章。同一 GAM 位元組內容可能對應不同歷史，未修改 GAM 的設計無法偵測玩家手動交換兩份相同 GAM 的 MLG；接受此限制，使用者須整對搬移。正常引擎保存靠交易協議維持關聯。

歷史附屬檔缺失、驗證失敗、未知格式或字碼映射不符：原 GAM 可正常載入；清楚提示歷史不可用，建立含缺口標記的新工作紀錄。不能靜默呈現亂碼或把前一條歷史留下。

若執行中紀錄 append 失敗：繼續遊戲，停用後續 append 並保留可驗證前綴，給一次提示。後續存檔可保存「有缺口」的有效歷史。若目標磁碟無法寫出完整的一對檔案，該次存檔回報失敗並保護舊槽，不可仍顯示「快速存檔完成」。錯誤提示自身不得進紀錄。

## 7. 檔案格式與記憶體建議

第一版使用版本化 binary，DOS 端直接存已展開的遊戲編碼文字；不在執行時轉 UTF-8。需要人讀／診斷時由 Python 工具輸出 UTF-8。此節是格式邏輯草案，實際 byte offset 表與 golden fixture 要在施工第 1 階段凍結。

標頭至少有：magic、format version、header length、flags（完整／缺口／快照或工作檔）、encoding ID、字碼 mapping 指紋、綁定 GAM 長度／CRC32、已提交資料尾端、事件數與檔案完整性校驗。

事件至少有：record length、kind、事件序號、conversation ID、前筆 offset、現實日期時間、章節／zone／scene ID、來源 DDX 檔案識別和 key、speaker ID（可未知）、人物／地點顯示名稱快照、已展開本文、各字串 byte length、事件校驗值。可使用 conversation begin／text span／choice／gap／end 等 kind；未知可選 kind 依 length 跳過，未知主格式版本拒絕。

- 所有整數明確 little-endian，以欄位寫入；禁止直接 fwrite C struct，避免 16 位元編譯器 packing／指標大小差異。
- 檔案 offset、長度累計、事件序號使用經確認為 32 位元的型別；seek 範圍不超過 signed long 能表達的上限。遇上限提示停記，不能整數回捲。
- 單次 I/O／配置建議 4–8 KiB，實際額度以引擎可用記憶體量測決定；單筆超限分成連續片段，中文雙位元字不能切斷。
- 不以巨大 near array 或整檔 malloc 讀歷史；不保留 DDX 被釋放後的 pointer；共享 scratch buffer 的內容必须在下一次使用前複製／寫入。
- 清單讀固定數量摘要，前筆 offset 可反向找到最近事件；conversation 聚合允許串流掃描或可重建磁碟索引。索引不是歷史真相，不能要求索引損壞就丟失本文。
- 使用獨立唯讀 viewer 路徑，不可呼叫 `dialog_play_record()` 重播原 DDX，否則可能再次給物品、改任務旗標。
- 保留當時已解析的人物／地名／文本，不只保存 resource ID。後來翻譯更新不應改寫歷史原文。
- 遊戲雙字節字碼依 mapping 決定含義；標頭記錄 mapping 指紋，版本更新若更動映射需要離線轉換或安全拒絕，不能只比較字型檔名。

### 擷取粒度

token 展開後、文字緩衝被覆寫前，取得正文與標題。`@0..@5` 有時是金額／數值，不保證是 NPC，說話者須由實際 speech 上下文判定；無法判定顯示「未知說話者」或「旁白」，不可捏造。

內容只加入已經呈現的文字範圍。多頁文本第一次只記第一頁，往下翻才補下一頁；回看不重記。陰影與主文 render 只記一次。用「本次 display instance + 文本範圍」去重，不用 DDX key 全域去重。玩家跳過尚未顯示的劇情頁不得提前記錄；任何擷取 hook 都不能改變原播放節奏。

地點擷取當下快照：城鎮／室內有名稱就用名稱；無名稱 fallback 為「區域 N」等可理解標籤，另存 zone／scene／座標供診斷。不可用讀紀錄當下所在地覆蓋歷史地點。

### 容量量級

假設每段本文 500 bytes、人物／地點／欄位平均 200 bytes，10,000 段約 7 MB；20 份手動 + 20 份快存 + 10 份自動存檔各有完整同等歷史，約 350 MB，另加工作檔和交易暫存。這是估算，不是實測；實際目錄數可更多，總量沒有 50 份的硬上限。

磁碟容量通常可接受，但 DOS 複製速度、每次 autosave 暫停時間和空間不足更值得測量。第一版不引入共用歷史 DAG／壓縮／雲端同步；若 1／5／10 MB 樣本保存延遲不可接受，再根據數據另提格式改版，不能私自改成只存最近 N 筆。
